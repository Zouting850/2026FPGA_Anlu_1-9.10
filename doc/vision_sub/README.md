# 视觉处理副板 · M1 / M2 / M3 / M4 / M5 里程碑

> 副板核心：安路 **EG4S20BG256**（康芯 HX4S20 开发板）
> 传感器：逐飞总钻风 **MT9V034 V2.1**（全局快门灰度，8bit DVP）
> 上游方案：`docs/视觉处理副板设计方案-v2.0-引脚接口确定版.md`

本目录记录副板各里程碑的实现、接线与验收方式。

- **M1**（SCCB 配置 + DVP 采集 + 帧指纹）把"FPGA 能不能自己把摄像头配起来、能不能正确采到像素"
  这件事**独立闭环**，不依赖主板、不依赖 SDRAM、不依赖任何后续算法。
- **M2**（背景建模 + 帧差二值化 + 前景统计）把"FPGA 能不能自己把画面里的运动目标抠出来"
  独立闭环：同样不依赖主板、**不依赖 SDRAM**（背景帧是 88 KB 的**片内 ERAM 单缓冲**）。
  ⚠️ 2026-09-14：单一 9K 阵列装不下，已改为 **16 × ERAM32K + 32 × ERAM9K 片上混合**——见 §9.5 与 §11.4。
- **M3**（形态学开运算 + 行列投影 + 人数分段）把"FPGA 能不能把二值前景整理成可判读的
  投影曲线、并给出一个人数估计"独立闭环：仍然不依赖主板、不依赖 SDRAM——投影直方图用
  寄存器阵列而非 BRAM，整条链仍是**纯流式、单缓冲**。
- **M4**（自动曝光闭环）把"FPGA 能不能自己把亮度稳在目标值"独立闭环：关掉传感器片上
  AEC/AGC、由 FPGA 回写 R0x0B/R0x35。这一级是 M2/M3 能不能**长期稳定**的前提——
  片上 AEC 随场景微调曝光，整帧灰度集体平移，帧差满屏假前景，背景模型会被反复冲垮。
- **M5**（行为状态机 + 置信度）把"FPGA 能不能把逐帧的瞬时量读成**行为**"独立闭环：
  有人来了 / 站定了 / 几个人 / 在互动 / 离开了多久 → `(状态, 建议模式, 置信度)` 三元组。
  这是副板**第一次给出主板能用的决策依据**（但仍只给建议，裁决权在主板）。

## 1 M1 目标与验收

| 目标 | 验收手段 | 通过判据 |
|---|---|---|
| 用 FPGA 经 SCCB 配置 MT9V034 | 读回 `R0x00`（芯片版本） | `= 0x1324`，且串口自检标志位 = `K` |
| 正确采集 DVP 像素流 | 串口打印的帧指纹 | `N = 90240 = 376×240`，且 `L/H` 随场景变化 |
| 60 fps 无丢帧 | 帧计数与秒表对照 / 逻辑分析仪抓 VSYNC | 每秒约 60 帧，`S` 每帧更新 |

> `R0x00 = 0x1324` 是 MT9V034 的固定只读常量（见 Aptina *MT9V034 Register Reference*），
> 因此它是"这条 SCCB 链路真的通到了传感器"的最强证据——不是回读我们自己写进去的值。

> **为什么 `vision_def.v` 和其他 HDL 平铺在同一层**：TD 解析 `` `include "xxx.v" `` 时，
> 可靠的做法是让头文件与引用它的文件同目录（本仓库 `marquee_font.vh` 与
> `marquee_overlay.v` 就是这个模式）。放进子目录会让 `` `include `` 的搜索路径
> 变得依赖工程配置，容易变成找不到文件的编译错误。


> **为什么 M1 顶层不例化 SDRAM/PLL**：M1 只需 50 MHz 板载时钟即可验证"配置 + 采集 + 统计"。
> 行缓存与 SDRAM 三缓冲帧缓存属 **M1b**（需 TD 的 SDRAM 控制器 IP）。
> 这样 M1 的验证不引入 SDRAM 时序变量，出问题时定位面更窄。
>
> ⚠️ **2026-09-14 修正**：M2 沿用了"先不用 SDRAM"的思路，把背景帧放进片内 BRAM。
> 真实构建证明**放不下**（`PHY-9013`，见 §9.5 二次修正与 §11.4）。
> 结论：**SDRAM 不再是"M1b 以后再说"的可选项，而是 M2 起就必须有的基础设施**。
> 帧缓存方案定论后，M1 顶层也建议同步引入 `sdram_ctrl.v`，让各里程碑共用同一套存储层。

## 3 SCCB 寄存器配置表

配置流程：**先软复位 → 设扫描模式/几何 → 最后开 binning**，末了读 `R0x00` 校验。
表由 `vision_def.v` 用宏定义，`mt9v034_cfg.v` 顺序索引（顺序不能乱）。

| 序 | 寄存器 | 值 | 含义 |
|---|---|---|---|
| 1 | `R0x0C` Reset | `0x0001` | 复位数字逻辑（自清零） |
| 2 | `R0x07` Chip Control | `0x0388` | 逐行 + 主模式 + 单色 |
| 3 | `R0x01` Column Start | `0x0001` | 列起始 |
| 4 | `R0x02` Row Start | `0x0004` | 行起始 |
| 5 | `R0x03` Window Height | `0x01E0` | 480 行（binning 前） |
| 6 | `R0x04` Window Width | `0x02F0` | 752 列（binning 前） |
| 7 | `R0x0D` Read Mode | `0x0305` | **2×2 binning** |
| 8 | `R0xAF` AEC/AGC | `0x0003` | 使能 AEC + AGC |
| — | `R0x00` Chip Version | 读回 `0x1324` | **自检**，不符则重试 |

### 3.1 两个容易踩的坑（已由模型验证）

**`R0x0D` 的 bit[9:8] 是固定为 1 的**。它的位域是 `0000 0011 dddd dddd`，
所以 2×2 binning 要写 **`0x0305`**（`0x0300 | bit0 行bin2 | bit2 列bin2`），
**不是** `0x0005`。只写 `0x0005` 会破坏固定位。

**SCCB 读操作的 ACK 规则**：16 位读时，主机作为接收方必须
**ACK 数据高字节 `D_H`、只 NACK 最后一个字节 `D_L`**。
若把 `D_H` 也 NACK 掉，从机会在 `D_H` 后释放 SDA，导致 `D_L` 读成 `0xFF`，
版本值就会变成 `0xFFxx` —— 这正是 M1 早期版本的真实 bug。

> ⚠️ 前提：已完成 **M0 硬件改造**——拆掉总钻风板载 51 单片机 + 焊接 R12/R13，
> 使 FPC 的 TXD/RXD 变成 SCCB 的 SCL/SDA。未改造则无法用 FPGA 配置传感器。

| 转接板 P1 | 信号 | → J1 脚位 | FPGA 引脚 | 顶层端口 |
|---|---|---|---|---|
| 1 | PCLK_OUT | 1 | D14 | `cam_pclk` |
| 2 / 4 / 6 / 8 / 10 / 12 / 14 / 16 | D0–D7 | 2/3/4/5/6/7/8/9 | G11 G12 F13 H13 H14 J14 J13 K12 | `cam_d[7:0]` |
| 9 | HREF | 10 | L14 | `cam_href` |
| 11 | VSYNC | 13 | M14 | `cam_vsync` |
| 5 | TXD | 14 | P11 | `cam_scl` |
| 7 | RXD | 15 | L10 | `cam_sda` |
| 3 / 13 | GND | 12/30 | — | — |
| 15 | 3V3 | 29（经独立 LDO + π 滤波） | — | — |

> ⚠️ **TXD/RXD 谁是 SCL 未在手册中指明**。改造后 FPC 的 TXD/RXD 变为 CMOS 的
> SCL/SDA（见《总钻风摄像头使用说明 V2.7》§7.2），但该节**没有说明对应关系**；
> 转接板 V3.1 又原样透传到 J1-14/J1-15。实物接线是 50/50 的两可。
> **无需赌线序**：`mt9v034_cfg.v` 上电先以极性 0 单次读 `R0x00`，命中 `0x1324`
> 即锁定；否则换极性 1 再读一次；两次都失败才判 `cam_ok=0`（此时是线路/上拉/供电
> 问题，不是接反）。探测只发"读"事务、不写任何寄存器，不会扰动传感器。

板载资源：`sys_clk = R7`、`rst_n = KEY1/A2`、调试串口 `uart_rx = F12` / `uart_tx = D12`、
LED `A4 A3 C10 B12`。摄像头 3V3 **不从扩展口取电**，由副板独立 LDO 供给。

LED 指示：`led[0]` 配置完成、`led[1]` 自检通过(`cam_ok`)、`led[2]` 0.5 s 内有新帧、`led[3]` 4 Hz 心跳。

## 5 调试串口输出格式

115200-8N1，**52 字节定长**，每秒一行（配置完成瞬间额外补发一次）：

```
MH1 K V=1324 S=0123ABCD N=016080 L=00 H=FF P0=1324\r\n   ← 正常
MH1 W V=1324 S=0123ABCD N=016080 L=00 H=FF P0=1324\r\n   ← 两线接反，已自动换向
MH1 F V=0000 S=00000000 N=058200 L=00 H=00 P0=FFFF\r\n   ← 两种极性都不通（实测）
```

| 字段 | 含义 |
|---|---|
| `MH1` | 固定标识（副板 M1） |
| `K` / `W` / `F` | SCCB 自检通过 / 通过但两线接反已自动换向 / 失败 |
| `V` | **最后一次**读回的芯片版本，应为 `1324` |
| `S` | 本帧像素灰度累加和（32bit） |
| `N` | 本帧有效像素数，应 = `016080` = 90240 = 376×240 |
| `L` / `H` | 本帧最小 / 最大灰度 |
| `P0` | **诊断**：第一次（极性 0）探测读到的 R0x00。与 `V` 对照即可定位故障线 |

判读要点：
- **`K` / `W` + `V=1324`** → SCCB 通、传感器在线（`W` 说明实物线序与标注相反，
  已被探测逻辑换向，功能不受影响）；
- **`N=016080`** → binning 生效、行场定时对（若 `R0x0D` 写错会得到 188×120 之类的数）；
- **`S/L/H` 随手遮挡镜头变化** → DVP 数据线真在传真实像素，而非常量；
- **`F` 时看 `V` 与 `P0`**：两者一大一小（如 `V=0000 P0=FFFF`）说明
  两根线里有一根被拉低（短路/下拉/断线）；两者都是 `FFFF` 说明
  两根线都没有任何器件在应答（断路、或改造没把 IIC 引出来）。

> **典型故障：`MH1 F V=... P0=... N=058200`**
> `F` = SCCB 自检失败、`V`/`P0` = 两次探测各自读到的总线值、`N=058200` = `752×480` = 传感器
> **上电默认几何**。含义是**整张配置表（含 `R0x0D=0x0305` 的 2×2 binning）根本没写进
> 传感器**，传感器停在默认 752×480、AEC 开。此时 DVP 那 11 根线仍照常工作，所以
> 串口上 `S/L/H` 在变、**只有 `V` 和 `N` 恒定** —— 表现为"转动摄像头时读数大量不变"。
> 两种极性都探不到 ⇒ 不是接反，而是 SCL/SDA 断路、缺上拉、或摄像头未供电。

M2 顶层（`top_vision_m2.v`）沿用同一套机架，状态行改为 **53 字节**、标识 `MH2`：

```
MH2 K N=016080 L=11 H=EE F=00ABCD B=00A,014,12C,0C8\r\n
```

| 字段 | 含义 |
|---|---|
| `MH2` | 固定标识（副板 M2） |
| `K` / `W` / `F` | SCCB 自检通过 / 接反已自动换向 / 失败（沿用 M1） |
| `N` | 本帧有效像素数，应 = `016080` = 90240（几何回归） |
| `L` / `H` | 本帧最小 / 最大灰度（防"画面恒定"被误判成完美静态） |
| `F` | **本帧前景像素数**；静止场景应 → `000000` |
| `B` | **前景包围盒** `minx,miny,maxx,maxy`（各 3 位十六进制）；无前景时全 `000` |

LED 指示：`led[0]` 配置完成、`led[1]` 自检通过、`led[2]` 0.5 s 内有新帧、`led[3]` 背景装载完成。

M3 顶层（`top_vision_m3.v`）状态行扩到 **141 字节**、标识 `MH3`，把整条列投影曲线**直接打成 ASCII 曲线**：

```
MH3 K N=016080 F=0000A3 M=00001C P=2 S=068 V=0000112233445566778899AABBCCDDEEFF00112233...
```

| 字段 | 含义 |
|---|---|
| `MH3` | 固定标识（副板 M3） |
| `K` / `W` / `F` | SCCB 自检通过 / 接反已自动换向 / 失败（沿用 M1/M2） |
| `N` | 本帧有效像素数，应 = `016080` = 90240（几何回归） |
| `F` | **形态学前**前景像素数（原始帧差，沿用 M2 的 `fg_stat`）；静态应 → `000000` |
| `M` | **形态学后**前景像素数；与 `F` 对照即"开运算压掉了多少噪点" |
| `P` | **人数估计**（列投影分段数，饱和 15，1 位十六进制） |
| `S` | **占用列数** = 占用列箱数 × 4（3 位十六进制） |
| `V` | **列投影曲线**：94 个十六进制字符，每字符 = 对应 4 列的前景像素和 `>> 6` |

`V` 曲线的一个 hex 字符取值范围 `0..F`（列箱上限 4×240 = 960，`960 >> 6 = 15` 恰好落满一位十六进制）。
把它按字符读出来就是一条左右方向的**水平投影峰形**：站着一个人→一个峰，两个人并肩→两个峰，
峰的位置就是人的水平位置。这正是 §8.1 验收里"峰值数与人工目视一致"的量化依据。

LED 指示（M3 沿用 M2）：`led[0]` 配置完成、`led[1]` 自检通过、`led[2]` 0.5 s 内有新帧、`led[3]` 背景装载完成。

M4 顶层（`top_vision_m4.v`）状态行扩到 **164 字节**、标识 `MH4`，在曲线之前插入四个曝光闭环字段：

```
MH4 K N=016080 F=0000A3 M=00001C P=2 S=068 E=0100 G=010 Y=060 L=1 V=00001122...\r\n
```

| 字段 | 含义 |
|---|---|
| `MH4` | 固定标识（副板 M4） |
| `K` / `F` | SCCB 自检通过 / 失败（沿用 M1–M3） |
| `N` / `F` / `M` / `P` / `S` | 与 M3 同义（像素数 / 形态学前 / 形态学后 / 人数 / 占用列数） |
| `E` | **当前曝光值**（R0x0B 粗快门总量，4 位十六进制） |
| `G` | **当前模拟增益**（R0x35，3 位十六进制；闭环只在快门到限时才动它） |
| `Y` | **本帧平均灰度**（0–255，闭环的直接观测量；目标 96） |
| `L` | **曝光锁定标志**（1 = 已连续 `EXP_LOCK_FRAMES` 帧落在死区内） |
| `V` | 列投影曲线（与 M3 同义，仍是行尾 94 个字符） |

判读要点：
- **`Y` 收敛到约 `060`** → 曝光闭环工作正常；
- **`L=1` 且 `E` 不再变化** → 收敛且无振荡（M4 的核心验收证据）；
- 遮挡镜头时 `Y` 先跌、随后 `E` 增大把 `Y` 拉回来 → 闭环方向正确；
- **`E` 到 `0008` 后 `G` 开始变化** → 快门已到下限，增益兜底接管。

LED 指示：`led[0]` 配置完成、`led[1]` 自检通过、`led[2]` 0.5 s 内有新帧、`led[3]` **曝光锁定**。

M5 顶层（`top_vision_m5.v`）状态行扩到 **193 字节**、标识 `MH5`，在 `L=x` 与 `V=` 之间插入 29 字节行为字段：

```
MH5 K N=016080 F=0000A3 M=00001C P=2 S=068 E=0100 G=010 Y=060 L=1 T=2 Q=1 C=B4 D=0078 I=01 U=1 V=<94 hex>\r\n
```

| 字段 | 含义 |
|---|---|
| `MH5` | 固定标识（副板 M5） |
| `K` / `N` / `F` / `M` / `P` / `S` / `E` / `G` / `Y` / `L` | **与 M4 逐字段同义**（SCCB 自检 / 像素数 / 形态学前 / 形态学后 / 人数 / 占用列数 / 曝光 / 增益 / 平均灰度 / 曝光锁定） |
| `T` | **行为状态**（1 位十六进制）：`0`=IDLE `1`=PRESENCE `2`=SINGLE `3`=MULTI `4`=INTERACT `5`=LEAVE `6`=ALERT |
| `Q` | **建议播放模式**（1 位十六进制）：`0`=STANDBY `1`=SINGLE `2`=MULTI `3`=INTERACT `4`=ALERT |
| `C` | **置信度** 0..254（2 位十六进制）；≥128 建议采信，<64 建议忽略 |
| `D` | **停留帧数**（4 位十六进制，60 帧 = 1 s；进入 LEAVE 后停更，锁定"看了多久"） |
| `I` | **互动次数**（2 位十六进制，饱和） |
| `U` | **死区滤波后人数**（与 `P` 对照看：两者之差就是死区正在吸收的抖动） |
| `V` | 列投影曲线（与 M3/M4 同义，仍是行尾 94 个字符） |

**字节账**：`66`（M4 公共前缀，含尾随空格）+ `29`（M5 字段）+ `2`（`V=`）+ `94`（曲线）+ `2`（CRLF）= **193**。
字段位置经模型逐字节校验：`V` 落在 95、曲线 97..190、CR 191 / LF 192。
因为前缀与 M4 **完全对齐**（只有 `MH4`→`MH5`），同一套日志解析脚本不用改就能同时读 M4/M5。

判读要点（M5 的验收证据就在这三个字段）：
- **有人走进画面** → `T` 由 `0` 变 `1`(PRESENCE) 再稳定到 `2`(SINGLE)，同时 `C` 从低位往上爬；
- **两个人** → `T=3`(MULTI)、`Q=2`；`U` 与 `P` 不一致时说明死区正在挡未确认的人数抖动；
- **挥手** → `T` 短暂进入 `4`(INTERACT)、`I` 计数 +1，`D` 继续累加；
- **人走开** → `T=5`(LEAVE)，`D` 冻结在离开前那一刻的停留帧数；
- `Q` 只是**建议**——按方案 §2.2，最终裁决权在主板。

LED 指示（M5 **沿用 M4，不新增**）：`led[0]` 配置完成、`led[1]` 自检通过、`led[2]` 0.5 s 内有新帧、`led[3]` 曝光锁定。
板载只有 4 颗 LED 且 M4 已占满；M5 的证据改由 `T=`/`Q=`/`C=` 三个串口字段承担——这也是"里程碑一经验证即冻结"原则的体现。

**⚠️ TD 6.2.1 无头构建的坑（全部实测踩过，别再踩）**：

1. **不要用项目模式 `launch_runs`/`wait_run`**（`td_headless.tcl` 那条路）：综合在
   td_commands_prompt 进程内跑完不落盘，一旦进程退出结果全丢；`reset_runs` 还会
   **级联重置依赖的 syn run**，把已有产物清掉；`wait_run` 对"子进程秒死"不感知，
   永远打印 Waiting。
2. **运行目录的 `settings.cfg` 若由项目模式重新生成，`device_name`/`package_name`
   会是空值** → `import_device` 失败，run.exe 只留横幅即死。手工补上：
   `set device_name eagle_s20.db` / `set package_name EG4S20BG256`。
3. **TD 自己生成的 `run.bat` 是坏的**：exe 名拼接错误（`td_commands_prompt_commands_prompt.exe`），
   且未包退出包装。忽略 run.bat，直接按上面的命令行调用。
4. `td_build.ps1` 的默认路径是旧机器的（`d:\Nizhenghang\...`、`D:\Download\TD`），
   本机 TD 装在 `D:\TD\`，用前需改参数；其"运行目录流"原理与上面一致。
5. Git Bash 里杀 TD 进程用 `MSYS2_ARG_CONV_EXCL='*' taskkill /F /PID <pid>`；
   本会话的 PowerShell 工具不回显输出，进程排查一律用 `tasklist` 而非 Get-Process。
6. M2/M3/M4/M5 的 `.al` 首次打开后同样会生成运行目录；若 `settings.cfg` 出现空值按第 2 条补齐即可。
7. **运行目录流真正打开的是 `.prj` 快照，不是 `.al`**（`DefaultFlow.tcl` 里执行的是
   `open_project <prj>.prj`）。TD **只在"创建运行目录"那一次**写这个快照；运行目录一旦已存在，
   `open_project <.al>` 就不再写它。此时 syn 会以"零个设计文件"开跑，唯一症状是：
   ```
   PRJ-1401 : Successfully analyzed 1 source files.     <- 只有 1 个，正常是十几到二十几个
   HDL-8001 ERROR: Incorrect top-level module name "top_vision_m5", please reset
   ```
   这个报错**方向性极差**（像是顶层名字写错了），实际根因是 `.prj` 缺了或内容不对。
   快照丢了/要重建，用：
   ```bash
   python tools/td_make_prj.py src/vision_sub/td_project/vision_sub_m5.al \
                               src/vision_sub/td_project/vision_sub_m5_Runs/syn_1/vision_sub_m5.prj
   ```
   `td_make_prj.py` 把 `.al` 确定性地转成 `.prj`（3 处变换 + 重标 `AutoExcluded`），
   **已用 M1 的真实 `.prj` 做过逐字节验证**（除 `RunTime` 外完全一致）。
8. **`.al` 里的 `AutoExcluded="true"` 只能标在"不含 `module` 的纯 `` `include `` 文件"上**
   （本项目就是 `vision_def.v`）。若它被误标到模块文件上，TD 会把这些文件**排除出读取列表**，
   于是 elaborate 空转、报上面那个 `HDL-8001`。`vision_sub_m4.al` / `vision_sub_m5.al`
   曾各带 15 个误标（从一份"源文件当时不在工作副本里"的旧快照派生而来，`m5.al` 又继承了
   `m4.al`），2026-09-14 已修正为"只有 `vision_def.v` 被标"。**派生新 `.al` 时务必核对这一项**：
   ```bash
   grep -c AutoExcluded src/vision_sub/td_project/vision_sub_m5.al   # 应为 1
   ```
9. **别用 `tail -f /dev/null |` 来"保持 stdin 不 EOF"**：管道里的 `tail` 永不退出，
   bash 认为整条管道没结束，后台 shell 的 cwd 就一直停在运行目录里 → 该目录**无法
   rename/删除**（文件仍可写，所以现象很迷惑）。实测 `td_commands_prompt.exe <tcl>`
   **不给 stdin 也能正常跑完并退出**，直接跑更干净。
10. **强杀 TD 会留下 `td_project/.lock.f`**（里面记着已死的 PID）和**孤儿 `td.exe`**
    （GUI 进程，实测可涨到 560 MB，会占住项目目录）。杀完记得删 `.lock.f`。
11. Git Bash 里 `grep -q $'\r'` 判断换行符不可靠；要确认 CRLF 用 Python 数 `\r\n` 与 `\n`。
    MSYS 风格路径 `/d/TD/...` **不能传给 Windows 的 Python**（会变成 `D:\d\TD\...`），要写 `D:/TD/...`。


### 6.3 上板验收步骤

1. 接好摄像头（先核对 J1 第 1 脚方向：正方向**左上**），上电；
2. 打开串口助手 115200-8N1，观察是否每秒一行 `MH1 K V=1324 ... P0=1324`
   （**`MH1 W` 也可通过**：表示两线接反但已被自动换向，见 §11.7）；

   （若看到 `MH1 F ... N=058200`，是 SCCB 未通、传感器停在上电默认 752×480 —— §11.7/§11.8）
5. **改线后不必重新烧 bit**：`cam_ok=0` 时探测每 2 s 自动重来一次（§11.8），
   所以修好上拉/接线后**最多等 2 秒**串口就会自己变成 `MH1 K` / `MH1 W`。
5. 用示波器/逻辑分析仪量 `cam_pclk` 实际频率（预期 ≈13.5 MHz），记录到待核对项。

## 8 M2 里程碑：背景建模 + 帧差二值化

M2 的目标是把"画面里的运动/异物目标"从背景里抠出来，并给出**逐帧可判读的量化证据**
（前景像素数 + 前景包围盒），为 M3 的形态学/投影/M4 的曝光闭环打好输入。

### 8.1 目标与验收

| 目标 | 验收手段 | 通过判据 |
|---|---|---|
| 背景能自学习并稳定 | 静止场景下串口 `F` 字段 | 装载结束后 `F=000000`，包围盒 `B=000,000,000,000` |
| 目标出现能被检出 | 在镜头前挥动某物 | `F` 明显 > 0，`B` 落在挥动的区域 |
| 目标离开后能恢复 | 目标移出后继续观察 | `F` 逐步回落到 0 |
| 无符号溢出 | 全暗/全亮场景（`cur`、`bg` 取 0/255 边界） | 不出现满屏假前景 |
| 前景统计与像素对齐 | 模型逐周期校验 | 包围盒不整体偏移 1 像素 |

LVDS/串口输出格式见 §5（M2 状态行 53 字节，标识改为 `MH2`）。

### 8.2 算法与实现

**逐像素、全无符号**的漏积分器（`bg_model.v`）：

```
d    = |cur − bg|                      幅度 0..255
fg   = (d > FG_THRESH)                 前景判定位（1 = 前景）
want = fg ? 1 : max(1, d >> BG_SHIFT)  本帧想挪几级
step = min(want, d)                    ← 钳位（关键，见 §8.3）
bg'  = (cur ≥ bg) ? bg + step : bg − step
```

**前景像素每 `FG_DIV` 帧才挪 1 级**（≈7.5 级/秒 @60fps），于是：
站立的人不会被立刻吸收（对比度 `C` 的前景要 `(C−FG_THRESH)×FG_DIV` 帧才融合，`C=100` 约 10 s、
`C=150` 约 17 s），人离开后的残影也在同一量级上消退。这两个时间常数是鲁棒性与响应速度的折中。

**为什么不用 SDRAM**：像素是**按光栅顺序流式**处理的——同一位置每帧只访问一次（读出旧背景、
就地写回新背景），所以 376×240×8bit = **88 KB 的单缓冲**足够（`bg_store.v`，BRAM 单缓冲，
无复位以便 TD 推断 ERAM9K；读写地址恒差 1，不存在同地址冲突）。SDRAM 三缓冲留给需要整帧随机访问
的场合（M1b）。

**装载阶段**：BRAM 上电内容未定义，若直接拿它当背景，开机满屏假前景（而前景像素每 `FG_DIV`
帧才走 1 级，靠算法收敛要好几十秒）。因此复位后前 `BG_LOAD_FRAMES`(=16) 帧强制 `bg ← cur` 且
`fg` 恒 0。

**模块流水线**（`m2_engine.v`，PIXCLK 域，与 `dvp_capture` 同域）：

```
拍 t   ：pix_valid=1，坐标 (x,y) 与线性地址 idx；rd_en=1, rd_addr=idx
拍 t+1 ：得旧背景，bg_model 算 fg / bg_next；wr_en=1, wr_addr=idx-1, wr_data=bg_next
拍 t+2 ：输出四路同拍 (fg_valid, fg, fg_x, fg_y)
```

`fg_stat.v` 在 PIXCLK 域逐帧累加前景像素数（17 bit）与前景包围盒，并在 `frame_start` 锁存上一帧
结果 + 翻转 `frame_done_tog`，顶层用与 M1 相同的握手同步到 sys 域取准静态快照。

### 8.3 模型抓出的两个 RTL 隐患（已修）

这两个 bug 都是"上板才会发作、而症状又极难反查"的类型，靠 `tools/sim_vision_sub_m2.py` 提前逮住：

1. **`d = 0` 的 8 bit 溢出**。`max(1, ·)` 消死区是对的，但它会让 `d=0` 时 `step=1`，
   于 `cur=bg=255` 时 `bg' = 255+1 = 256`，8 bit 回绕成 **0**；下一帧 `d=255`，**凭空造出满屏
   假前景**。修法：`step = min(want, d)`——`d=0` 不动、`d≥1` 照常 1 级/帧收敛，且 `bg'` 恒落在
   `[bg, cur]`。模型对全部 256×256 组 `(cur,bg)` 穷举校验了"永不越界 + 永不反向"。
2. **`fg` 未寄存导致的 1 像素错位**。`fg` 是组合逻辑（有效拍 `t+1`），而 `fg_valid/fg_x/fg_y`
   是寄存器（有效拍 `t+2`）。直接一起送 `fg_stat`，就会把"上一像素"的前景位算到"上上像素"的坐标上，
   效果是**包围盒整体偏移 1 像素、帧边界计数偏差**。修法：把 `fg` 也打一拍，四路输出才真正同拍。
   模型里保留了一个"去掉该寄存器就会错位"的负向对照。

另外记录一处**参数联动事实**（非 bug）：当前 `FG_THRESH(24) ≤ 2×2^BG_SHIFT(32)`，背景像素
`d≤24` 使 `d>>SHIFT` 只可能是 0/1，因此背景步长恒为 1 —— `BG_SHIFT` 的指数项**暂时不起作用**，
只有把 `FG_THRESH` 提到 `2^BG_SHIFT` 以上才会显现。

### 8.4 上板验收步骤（M2）

1. 按 §6.2 打开 `vision_sub_m2.al` 构建、下载；
2. 串口 115200-8N1，观察 `MH2 K N=016080 ...`；`led[3]` 亮表示背景装载完成；
3. **静止不动** 约 1 s，确认 `F=000000`、`B=000,000,000,000`；
4. 在镜头前挥手，确认 `F` 明显 > 0、`B` 落在手的那片区域；
5. 手移开，确认 `F` 在若干秒内回落到 0。

## 9 M3 里程碑：形态学 + 行列投影 + 人数分段

M3 的目标是把 M2 抠出来的**二值前景**整理成两条**投影曲线**（水平 / 垂直直方图），
再从中给出一个**人数估计**与占用范围，为 M5 的行为状态机、M6 的事件上报提供结构化输入。
整条链仍然**纯流式、不依赖 SDRAM**——M2 的背景帧单缓冲不变，M3 的直方图用**寄存器阵列**实现。

### 9.1 目标与验收

| 目标 | 验收手段 | 通过判据 |
|---|---|---|
| 压掉孤立噪点 | 串口同时打印形态学前后的前景数 `F` / `M` | 静止场景 `F`、`M` 都 → 0；抖动场景 `M < F` 且 `M` 明显更干净 |
| 水平投影正确 | 串口 `V` 字段的 94 个 hex 字符（ASCII 曲线） | 站一人 → 单峰；并肩两人 → 双峰；峰位与人的水平位置一致 |
| 人数估计正确 | 串口 `P` 字段 | 空场 `P=0`；一人 `P=1`；两人 `P=2`；与曲线峰数一致 |
| 占用宽度合理 | 串口 `S` 字段（占用列箱数 × 4） | 一人约 60–80 列；两人约为两倍 |
| 边界不误判 | 人在画面最左 / 最右边缘 | `P` 不因边缘截断而丢段或多段 |
| 无行漂移 | 模型逐周期校验行缓冲 | 连续多帧后投影峰位不整体偏移 |

LVDS/串口输出格式见 §5（M3 状态行 141 字节，标识 `MH3`，`V` 即 ASCII 投影曲线）。

### 9.2 算法与实现

**① 形态学开运算（`morph.v`，先腐蚀后膨胀）**

帧差二值图最烦人的是细碎的孤立噪点（传感器噪声、投影边缘抖动、曝光跳变），
它们在列投影上会把整列计数抬高一点点，撒够几列就会凭空多出一段。开运算正好治这个：
孤立点被腐蚀吃掉、膨胀也不会让它复活（开运算非扩展），而人形宽数十像素，
腐蚀只削一圈轮廓、膨胀再补回来，形状基本不动。

```
erode : e(x,y) = AND of 3×3 window     （窗口内全 1 才保留）
dilate: d(x,y) = OR  of 3×3 window     （窗口内有一个 1 就置 1）
open  : o = dilate(erode(fg))          （= morph.v 的 erode 级 → dilate 级级联）
```

**行缓冲为什么就是一个移位寄存器**：把一行像素按列序推进宽度 `W` 的移位寄存器，
第 k 个像素在 k 拍后到达左端被移出——所以"左端移出位" = `W` 拍前写入的像素。
一行恰好 `W = 376` 个有效像素，于是 `W` 拍前正好是**上一行的同一列**，
`lb0`/`lb1` 两级级联就得到相邻两行。**代价是每行必须严格 376 拍**（`m2_engine` 已保证），
否则行会一行一行地漂。也正因如此这里**不做"遇行首清零"**——清零会把要用的上一行数据清掉。

出口统一屏蔽边界（`x ≥ 2 且 y ≥ 2`），内部两级保持 `v` 全宽以避免行漂移。

**② 行列投影直方图（`projection.v`，4 列 / 4 行一箱）**

```
col_sum[k] = 第 4k..4k+3 列上的前景像素总数   → 水平投影曲线（人数分段看它）
row_sum[k] = 第 4k..4k+3 行上的前景像素总数   → 垂直投影曲线（人的上下边界）
```

- **为什么 4 列一箱而不是逐列 376 箱**：省资源（94×10bit + 60×11bit ≈ 1600 FF，读多路器 ≈ 1000 LUT；
  逐列要贵一倍多）、不损失可观测精度（串口曲线本就 1 字符 = 1 箱）、抗噪更好
  （相邻 4 列先加起来再判阈值，单列噪点不容易自己凑成一段）。人形约 60 列 = 15 箱，绰绰有余。
- **为什么用寄存器阵列而不是 BRAM**：BRAM 单口同拍只能干一件事，"累加读改写"与"读出清零"
  要么错拍要么绕逻辑。寄存器阵列的索引读是**组合多路器**、索引写是**译码器**，物理独立，于是
  累加可单拍读改写、读出可同拍读值+清零，**没有任何端口冲突，也不需要双缓冲**。
- **帧切换时序**：帧头起用 `94 + 60 = 154` 拍把上一帧两条直方图读出（边读边清零，
  顺手把曲线字符移入 `curve_bits`），最后一拍翻转 `viz_done_tog` 供顶层跨时钟域快照。
  154 拍 ≈ 11 µs @13.5 MHz。**读出期间关掉累加不会丢像素**：154 拍 < 一行 376 拍，
  只覆盖第 0 行，而 `morph` 恰好丢弃 `y < 4` 的行。
- **曲线打包是 msb-first**：新字符从**高位**进、已有内容右移 4 位，箱 0 停在最低 4 位；
  顶层串口从低位先吐，于是打印顺序就是箱 0→93 的从左到右顺序（详见 §9.3 的镜像 bug）。

**③ 人数分段（`people_seg.v`，吃读出流）**

```
col_occ = (bin > SEG_COL_THRESH)       二值化
连续占用箱连成一段；段内空洞 < SEG_MIN_GAP 箱则合上；
段宽 < SEG_MIN_WIDTH 箱的一律丢弃（残余噪点/反光点）；
存活段计数 = 人数估计 P
```

顺带记证据量：占用箱数 `occ`、首/末占用箱 `cf/cl`、峰值箱值 `cp` 及所在箱 `cpb`。
行相位同理按 `SEG_ROW_THRESH` 二值化，只保留首/末占用行箱，供后续画框/判越线。

**列最后一段的收尾**：列相位最后一个箱处理完可能还留着一个"开着"的段（画面最右边有人），
它在下一拍（行相位第一个箱，`ro_phase=1 && ro_bin=0`）统一收尾——这个条件用读出流本身就能判，
不需要额外端口。

> 人数 ±1 死区、进入/离开的滞回与确认属于 **M5 行为状态机**的职责，`people_seg` 只出
> "当前这一帧看起来有几个人"的瞬时值。

### 9.3 模型抓出的两个 RTL 隐患（已修）

这两个 bug 都是在**编写 RTL 的过程中**由 `tools/sim_vision_sub_m3.py` 提前逮住的，
都属于"上板能跑、但结果静悄悄地错"的类型（曲线镜像 / 最右一段漏数），肉眼极难发现：

1. **`ro_phase` 寄存导致的滞后**。最初把 `ro_phase` 写成了 `output reg`，它比组合的 `ro_bin`
   慢一拍：当 `ro_cnt = 94` 时 `ro_bin` 已经切到行箱 0，而 `ro_phase` 还停在列相位。
   后果有两处：`people_seg` 的收尾条件（`ro_phase=1 && ro_bin=0`）**永不成立**→ 画面最右的段漏数；
   同时行箱 0 会混进列统计。修法：`assign ro_phase = ~col_ph;` 改成**组合**，与 `ro_bin` 同步。
   模型里留了一个"把 `ro_phase` 寄存起来就会漂移行、泄漏行箱 0"的负向对照。
2. **曲线 lsb-first 打包造成的左右镜像**。最初写的是 `curve_bits <= {curve_bits[..:0], nib}`，
   把新字符塞进了**低位**，于是箱 0 跑到最高位；串口从低位先吐 → 打出来的曲线**整体左右镜像、
   峰位全反**。修法：改成 msb-first `curve_bits <= {nib, curve_bits[..:4]}`，箱 0 留最低 4 位，
   顶层保持"低位先吐"。模型里留了"lsb-first 打包会把曲线镜像"的负向对照。

另外清掉一处死代码（`people_seg` 里未使用的 `run_last`）。

> 这两个 bug 与 M2 的 §8.3 是同一类教训：**纯 Python 周期模型能在没有仿真器、没有板子的情况下，
> 把"时序差一拍""位序反了"这种最隐蔽的接线级错误在编码阶段就暴露出来。**

### 9.4 上板验收步骤（M3）

1. 按 §6.2 打开 `vision_sub_m3.al` 构建、下载；
2. 串口 115200-8N1，观察 `MH3 K N=016080 ...`（141 字节/行）；
3. **空场**：确认 `F=000000 M=000000 P=0 S=000`，`V` 全 0；
4. **站一人**：确认 `P=1`，`V` 出现一个峰，峰的字符位置 ≈ 人的水平位置，`S` ≈ 60–80；
5. **并肩两人**：确认 `P=2`，`V` 出现两个峰，间距 ≈ 两人水平距离；
6. **边缘一人**（贴左 / 贴右）：确认 `P` 仍 = 1（不因边缘截断丢段或多段）；
7. 对照 `F` 与 `M`：抖动场景下 `M < F`，说明开运算确实在压噪点。

### 9.5 资源核对（BRAM 预算修正）

上游方案 v2.0 §6 的 BRAM 估算（"约 10 块 ERAM9K"）是按**规划期**的粗估写的，实测/查手册后应为：

- **EG4S20BG256 的真实 BRAM = 64 × ERAM(9K) + 16 × ERAM(32K) = 1088 kbit = 136 KB**；
- M2 的背景帧 `376×240×8bit = 90240 B ≈ 88 KB = 704 kbit`，占全部 ERAM 的 **约 65%**；
- **M3 不新增 BRAM**：投影直方图是寄存器阵列（≈1600 FF + ≈1000 LUT），不占 ERAM；
- 因此剩余约 48 KB ERAM 仍可供 M4 曝光直方图等使用。

> 结论：BRAM 仍是整个设计最紧的资源，但 M3 的"寄存器阵列代替 BRAM"选择使预算没有被进一步挤压。
> 该修正项已回写设计方案 v2.0 §6。

> ### ⚠️ 二次修正（2026-09-14，真实构建实测）——上面这笔账算错了
>
> 上面的 "136 KB" 是**把两个物理互斥的池子加起来**得到的，而 TD 的布线器只按 **9K 池**判容量：
>
> | 池 | 容量 | TD 是否自动使用 |
> |---|---|---|
> | 9K EMB | **64 块 × 9 kbit = 576 kbit = 72 KB** | ✅ 推断 `reg [7:0] mem[..]` 就落在这里；TD 的 `emb` 上限 = 64 |
> | 32K EMB | 16 块 × `EG_PHY_BRAM32K`（2K×16 = 32 kbit）= 512 kbit = 64 KB | ❌ 需**手工实例化原语**，推断不会用 |
>
> 两个坑让 9K 池看起来比实际大得多：
>
> 1. **TD 把阵列深度向上对齐到 2 的幂。** `reg[7:0] mem[0:90239]` 报到 `#bram9k 128`
>    —— 那是把深度抬到 131072、再按 8K×1 打包的结果，约是理论下限的 **2 倍**。
>    （所以要把阵列深度**主动写成 2 的幂**，TD 的打包才可预测。）
> 2. 即便**理想打包**，9K 池也只有 `64 × 1 KB = 64 KB` 封顶。所以任何 >64 KB 的
>    单一阵列在 9K 池里**结构性装不下**，与写法无关。
>
> 于是 M2 的背景帧（`bg_store.v` = 90,240 B = **705 kbit**）单靠 9K 池装不下。真实 TD 报错：
>
> ```
> #bram   128  out of  64   200.00%          (syn 的 gate.area)
> PHY-9013 ERROR: Design's emb number = 128, exceeds the limit 64.
> ```
>
> 注意这**不是 M5 引入的问题**——M4 从未真正编译过，所以这面墙一直没被撞到；
> M5 是第一个一路走到 P&R 的里程碑。
>
> ### ✅ 三次修正（2026-09-14）：32K + 9K 片上混合，已解除阻断
>
> 路线定为**片上混合**（不引入 SDRAM，保持纯流式架构）。`bg_store.v` 改成两个池子拼：
>
> | 像素区间 | 落地 | 容量 |
> |---|---|---|
> | `[0 .. 65535]` | 16 × `EG_PHY_BRAM32K`，块内 2K×16 字，**一个字塞 2 个像素** | 16 × 2048 字 × 2 像素 = 65,536 B |
> | `[65536 .. 90239]` | 1 个 **32768** 深 × 8 位推断阵列（深度取 2 的幂） | 32 块 9K |
>
> 实测（M5 综合 + 布线）：`#bram9k 32/64` + `#bram32k 16/16`，**PHY-9013 消失**。
> 对外接口与 **1 拍读延迟完全不变**，所以 `m2_engine` / M3 / M4 / M5 的算法**一行没动**。
>
> 四个必须记住的实现细节（全部有实测背书）：
>
> 1. **块号必须并进片选。** 16 个原语共用同一组块内地址线，只靠 `csa`/`csb` 区分落在哪一块。
>    若给所有实例喂**相同的地址 + 相同的片选**，16 个实例输入完全一致 → TD 判定等价并合并，
>    `report_area` 静静报 `#bram32k 1 out of 16`，**白丢 15 块容量**（第一次综合就是这样，
>    差点带着这个 bug 去布线）。正确写法：
>    `wire csa_b = wr_en & pool_sel & (wr_word[14:11] == gi);`（`gi` 是 genvar，折叠成常数）。
> 2. **字节使能写**：`dia = {wr_data, wr_data}`、`bytewea = 1`、`bytea = addr[0]`。
>    同拍"同字读写"只会落在**不同字节**上（读 idx、写 idx-1），被读的字节永不被同拍改写，
>    所以**不依赖** BRAM 的 write-first / read-first 语义。
> 3. `REGMODE_x = "NOREG"`，保持 1 拍读延迟，下游流水线不动。
> 4. ERAM32K 物理上分布在 **IO 空隙**里（不在 PFB 阵列中），因此有位置约束，
>    TD 报错码 `USR-8043 非法的 BRAM32K 位置`。本设计用满 16 块 = 该池全部，不与其他模块争抢。
>
> 资源实测（M5 综合，最终版；已含 §11.5 除法修复与流水线改造）：
>
> ```
> #lut   5700 / 19600  29.08%      #bram9k   32 / 64   50.00%
> #reg   5608 / 19600  28.61%      #bram32k  16 / 16  100.00%
> #dsp      4 / 29     13.79%
> ```
>
> 其中 `behavior_fsm` 只占约 493 LUT / 157 FF —— **M5 本身几乎不花钱，曾经的唯一瓶颈全在
> M2 的帧缓存**（门级面积报告的层次分解显示：超限量 128 块**全部**来自 `u_m2/u_store`，
> 其他模块 bram 列都是 0；投影直方图走寄存器阵列确实没占 ERAM）。

## 10 M4 里程碑：自动曝光闭环

M4 的目标是把画面亮度**稳定**在目标值，而不是"看着好看"。这是 M2/M3 能不能长期稳定的前提：
片上 AEC 随场景持续微调曝光 → 整帧灰度集体平移 → 帧差满屏假前景 → 背景模型被反复冲垮。
M4 关掉片上 AEC/AGC，由 FPGA 自己闭环。

### 10.1 目标与验收

| 目标 | 验收手段 | 通过判据 |
|---|---|---|
| 亮度收敛 | 串口 `Y` 字段 | 遮挡/照亮镜头后 `Y` 在数秒内回到 `060` 附近 |
| 收敛后不振荡 | 串口 `E` 字段 | `L=1` 且 `E` 不再变化（模型里 100 帧零回写） |
| 快门优先、增益兜底 | 串口 `E`/`G` 对照 | 正常照度下 `G` 恒为初值 `010`；只有 `E` 到限位后 `G` 才变 |
| 削顶保护 | 高对比场景（强反光点） | 大量像素贴 255 时闭环主动压曝光，而不是被削顶的 sum 骗住 |
| 几何异常不误调 | 断开/接错排线 | `N≠016080` 时 `E`/`G` 保持不动 |

### 10.2 算法与实现

**寄存器语义**（MT9V034 数据手册 Table 7，已核准）：

| 寄存器 | 含义 | 角色 |
|---|---|---|
| `R0xAF` | AEC/AGC Enable | 配置表先写 `0x0003`（M1 沿用），M4 接管后写 `0x0000` |
| `R0x0B` | Coarse Shutter Width Total（粗快门总量） | **主调节量** |
| `R0x35` | Analog Gain Control（模拟增益） | 兜底调节量，快门到限才动 |

手册关键原文：多数寄存器在**帧起始**整体生效；但**快门宽度"下次曝光生效、n+2 帧图像才体现"**。
这直接决定了闭环的两条纪律（见下）。

**控制律**（`auto_exp.v`，比例步长，1 个乘法器，无除法器）：

```
err   = sum − TARGET_SUM              （>0 偏亮，<0 偏暗）
Δshut = (shut × |err|) >> EXP_PSHIFT  （≈ shut×|err|/TARGET，2^23 ≈ TARGET）
Δshut 钳到 [STEP_MIN, STEP_MAX]，且不越过快门/增益限位
偏亮：先减快门，快门到底减增益；偏暗：先加快门，快门到顶加增益
```

线性传感器（`sum ∝ shut`）下可推得 **`e' = −e²/T`**：误差按平方收缩、永不反向放大，
2~3 次回写即进死区。这正是"乘一个比例"而非"固定步长"的原因——**固定步长接近目标时
一定在死区两侧来回打**（模型的负向对照演示了这一点）。
`>> 23` 代替除法是因为 `TARGET_SUM = 8 663 040 ≈ 2^23`，3.2% 的比例偏差被死区吸收。

**两条时序纪律**：

1. **只在帧头（垂直消隐期）决策与下发**（`frame_tick` 由 `exp_meter` 的帧锁存翻转经
   两级同步派生，天然落在消隐期）——满足方案 §4.2"曝光回写必须对齐 VSYNC 消隐期"；
2. **两次回写至少隔 `EXP_UPDATE_DIV`=2 帧**（`div_cnt` 只在帧头计数）：写在第 N 帧头 →
   影响第 N+2 帧图像 → 第 N+3 帧头才量得到，恰好保证每次决策用的都是已生效的数据。

**饱和削顶保护**：帧内饱和像素数（≥250）超过 `EXP_SAT_MAX`(4096) 时强制判"偏亮"。
削顶会把 sum 压平，让闭环**低估**亮度而继续加曝光、把画面糊死；高对比场景（小面积强反光 +
大面积暗部）会被提前整体压暗——这是有意取舍：对背景建模，"不过曝"比"平均好看"重要。

**几何门限**：`cnt ≠ 90240` 时闭环冻结。窗口/接线坏掉时调曝光没有意义。

**资源仲裁**（`top_vision_m4.v`）：`sccb_master` 仍只有一个，`cfg_busy` 期间归
`mt9v034_cfg`，否则归 `auto_exp`。`cfg_busy` 从复位起就为 1，且 `auto_exp` 还要等
`cfg_done`——双保险，不存在两个控制器抢 `R0xAF` 互相打架的可能。

**为什么不复用 `frame_stat.v`**：M4 需要多一个"饱和像素数"，往 `frame_stat` 加端口就得
改动 M1 模块与模型。本项目"里程碑一经验证即冻结"，M4 只增不改——多一个约 60 FF 的
累加器，远低于回改 M1 再重新验证的代价（`exp_meter.v` 头注释有完整论证）。

### 10.3 模型抓出的 RTL bug 与设计取舍

1. **`div_cnt` 每拍自增导致写间隔守卫失效（真实 bug，已修）**。最初 `div_cnt` 在 `E_RUN`
   里每个时钟拍自增，`EXP_UPDATE_DIV=2` 意味着写完成 **2 个时钟拍**后就再次放行——
   "隔 2 帧"退化为"每帧可写"，闭环会拿 n+2 还没生效的旧亮度连算，等效步长翻倍、过冲
   风险大增。修法：把自增移进 `if(frame_tick)`，并重新推导出"写后隔 3 帧才放行、
   恰好在含新快门效果的测量之后"的时序。这是本项目的第三类"差一拍/差一帧"bug
   （M1 的 SCCB ACK、M2 的 fg 对齐、M3 的 ro_phase 之后，M4 的帧计数又来了一次）。
2. **设计取舍**：极端照度下快门+增益都到限位时闭环**停止调节、`L=0`**——不是 bug，
   是"诚实的不收敛"：物理上已经无能为力，锁定标志不该撒谎。模型对极亮/极暗两个场景
   断言了"停在双限位 + 停止回写"。
3. **快门/增益上下限（`SHUT_MIN/MAX`、`GAIN_MIN/MAX`）是纸面值**，需上板按实际镜头
   光圈与展项照度标定后回写 `vision_def.v`（已列入方案 §8.2 待核对项）。

### 10.4 上板验收步骤（M4）

1. 按 §6.2 打开 `vision_sub_m4.al` 构建、下载；串口 115200-8N1；
2. 正常照度下观察 `MH4 ... E=xxxx G=010 Y=060 L=1`——`Y` 稳在 `060` 附近、
   `E` 停止变化、`L=1`；
3. **遮挡镜头**：`Y` 先跌，随后 `E` 增大把 `Y` 拉回 `060`（闭环方向正确）；
4. **强光照射**：`E` 减小；若出现大面积过曝，确认闭环没有把画面推向全白；
5. **手电在镜头前打一个亮斑**（削顶场景）：确认 `E` 主动下降而不是被削顶的 sum 骗住；
6. 对照 `E` 与 `G`：正常照度下 `G` 恒为 `010`；只有把镜头完全捂死（`E` 到 `03FF`）后
   `G` 才开始增大；
7. 全程 `N=016080`，且 `M`/`P`/`S`/`V` 的行为与 M3 一致（M4 不应干扰前三级）。

## 11 M5 里程碑：行为状态机 + 置信度

M1~M4 只是把画面变成数字；**M5 才第一次给出主板能用的决策依据**。
但按方案 §2.2 的结论，副板只出 `(state, mode, conf)` 三元组，**最终裁决权在主板**——
副板不知道媒体清单、播放进度与内容分级，它报错时主板要能降级成定时循环而不是黑屏。

### 11.1 目标与验收

| 目标 | 验收手段 | 通过判据 |
|---|---|---|
| 有人靠近 | 串口 `T`/`Q`/`C` | 人走进画面后 `T` 由 `0` → `1` → 稳定到 `2`，`Q` 变 `1`，`C` 单调上升 |
| 多人区分 | 串口 `T`/`Q`/`U` | 两人并肩 → `T=3`、`Q=2`；`U` 与 `P` 不一致即死区在挡未确认的抖动 |
| 互动识别 | 串口 `T`/`I` | 挥手 → `T` 短暂 `4`、`I` 计数 +1，冷却期内不重复计数 |
| 停留时长 | 串口 `D` | 有人期间 `D` 每帧 +1；人走开 → `T=5` 且 `D` **冻结**（锁定"看了多久"） |
| 冷启动不误报 | 无人在场 | 上电后 `T` 恒为 `0`（IDLE），绝不自发进入 PRESENCE |
| 抗抖动 | 人在场轻微晃动 | `±1` 人数抖动不改变 `T`/`Q`（死区吸收） |
| 不与曝光闭环打架 | 遮挡/照亮镜头 | M4 的曝光调整引起全画面亮度平移时，`I` 不增加（§11.2 的两个陷阱） |

### 11.2 算法与实现

**状态与建议模式的映射**（`behavior_fsm.v`，纯 RTL 状态机，无软核）：

| 状态 `T` | 含义 | 建议模式 `Q` |
|---|---|---|
| `0` IDLE | 无人且久无动静 | `0` STANDBY |
| `1` PRESENCE | 刚检测到人，尚未站定 | `1` SINGLE |
| `2` SINGLE | 一个人站定 | `1` SINGLE |
| `3` MULTI | 两个及以上 | `2` MULTI |
| `4` INTERACT | 正在互动（挥手/前推） | `3` INTERACT |
| `5` LEAVE | 人刚离开（停留时长已锁定） | `0` STANDBY |
| `6` ALERT | 占用列触及画面最外侧警戒带 | `4` ALERT |

迁移条件（`frame_tick` 驱动，全部以"帧"为单位）：

```
IDLE            ── 人数≥1 连续 EVT_CONFIRM 帧 ──────→ PRESENCE
PRESENCE        ── 停止抖动且稳定 STABLE_FRAMES 帧 ──→ SINGLE
PRESENCE        ── 人数≥2 连续 EVT_CONFIRM 帧 ──────→ MULTI
INTERACT        ── 能量回落 或 冷却 COOL_FRAMES 到期 ─→ SINGLE/MULTI
SINGLE / MULTI  ── 占用范围触及最外 GUARD_EDGE 列 ───→ ALERT
任意"有人态"     ── 人数 0 持续 LEAVE_FRAMES ────────→ LEAVE（锁存 D）
LEAVE           ── 人数≥1 ────────────────────→ PRESENCE
LEAVE           ── 无人再持续 IDLE_HOLD_FRAMES ──→ IDLE
```

**防误触发四条**（方案 §2.2 的落地）：

1. **人数死区 + 同向确认**：与当前滤波值相差 `±1` 不认；同向变化要连续
   `PPL_CONFIRM`(=3) 帧才跟随；**差 ≥2 立即跟随**（真来了一群人不用等）。
   注意死区不是"把 2 人突发滤成 1 人"——短于 3 帧的突发被完全滤掉，长于等于 3 帧的
   持续**会被当真**；死区真正独立的贡献是让报告人数 `U` 稳定、并挡住"尚未确认的证据"。
2. **所有跃迁都要帧确认**：进入/退出用同一门限 `EVT_CONFIRM`(=3)，
   避免边缘抖动造成状态反复横跳。
3. **互动带冷却**：命中后驻留 `COOL_FRAMES`(=90, 1.5 s)，期间不再产生新的互动事件。
4. **质心安静判定**：质心每帧位移 ≤ `CTR_QUIET`(=3 箱) 才算"安静"，
   用于把"站着不动"与"在挥手"区分开。

**能量基线 EMA 与两个真实陷阱**（这一级最容易写错的地方）：

互动判据不能只看"前景像素数突然变大"——因为**人数变化本身就是能量阶跃**。
基线取一阶 EMA（`NRG_BASE_SHIFT`=5，即 1/32），并以两个陷阱为设计依据：

| 陷阱 | 现象 | 修法 |
|---|---|---|
| ① 上电基线为 0 | 第一个走进来的人 = 从 0 到 N 的"突增"，冷启动就误报一次互动 | `base_init`：**首个有效帧直接把基线灌成当前能量**，不走 EMA |
| ② 人数阶跃 | 第 2 个人走进来，前景像素数翻倍 → 被当成挥手 | 跟踪**原始人数** `ppl_i`；人数一变就清 `warm_cnt`，要连续 `NRG_BASE_READY`(=32) 帧基线才追上，期间不判互动 |

陷阱②的关键细节：`warm_cnt` 的清零是非阻塞赋值，若只用 `warm_cnt == READY` 判断，
人数阶跃那一帧读到的还是旧值，防护整整晚一拍——而能量跳变恰好就发生在这一拍。
所以组合条件里必须**同时**看 `pplr_chg`（原始人数变化），见 `behavior_fsm.v` 的注释。

**置信度合成**（无乘法器）：

```
sc_dwell  : 有人 +SC_UP，无人 −SC_DN     （待得久 → 可信）
sc_motion : 能量 ≥ NRG_LO 时 +SC_UP，否则 −SC_DN（真的有东西在）
sc_quiet  : 质心安静 +SC_UP，抖动 −SC_DN  （拿得准 → 可信）
conf = (sc_sum × 85) >> 8   ≈ sc_sum / 3.01，饱和 254
```

`×85` 用移位相加实现（`64+16+4+1`），`>>8` 用切片——整个 M5 不消耗任何乘法器。
三个分项各自饱和积分，所以短暂遮挡只会让 `C` 缓降而不会瞬间清零。

**几何坏帧**：`N ≠ 90240` 时状态机**冻结**（不跃迁），只让三个评分按 `SC_DN_SOFT` 缓降。
接错排线/丢帧时不该凭空改变行为判断。

### 11.3 TD 真实编译揪出的三类问题（模型全部抓不到）

M5 是本项目**第一个真正走到布局布线的里程碑**（M2/M3/M4 此前只过了 Python 模型）。
TD 一编译就抓出三个 Python 模型的结构性盲区——任意精度 + 不检查 Verilog 类型/顺序：

| # | 问题 | TD 的反应 | 后果 | 修法 |
|---|---|---|---|---|
| 1 | `IDLE_HOLD_FRAMES 9'd600` | 只有 `HDL-5007 WARNING` | **静默截断成 88 帧（≈1.5 s）**，而设计意图是 10 s | 改 `10'd600`（`idle_cnt` 本来就是 10 位） |
| 2 | `CONF_SHIFT 3'd8` | 只有 `HDL-5007 WARNING` | 截断成 0（当时未被引用，是潜伏雷） | 改 `4'd8` |
| 3 | `behavior_fsm.v` 的 `reg` 声明写在引用之后 | `HDL-5373 WARNING: used before its declaration` | 对 `pplf`/`ctr_p`/`nrg_base` 这类多比特量，早期工具会退化成**隐式 1-bit net** | 整个 `reg` 块前移到组合逻辑之前 |

> 教训：**"TD 没报 ERROR" 不等于"代码是对的"**。上面两条都是 WARNING 级，
> 但会静默改变行为。已把第 1/2 类问题固化成模型里的**位宽审计**
> （`test_define_widths`，带负控），改动 `` `define `` 后必跑。
> 第 3 类只能靠真实编译——所以**每个里程碑都要真的跑一次 TD syn**。

修复后 M5 综合结果：**0 ERROR**，无 `HDL-5007` / `HDL-5373`，
`elaborate module top_vision_m5` 正常，`Successfully analyzed 16 source files`
（17 个 HDL − 1 个 include-only 的 `vision_def.v`）。

> 第四类问题不是"报错"而是**时序不收敛**（一行显示用的除法把 sys_clk 域打穿），
> 见 §11.5——它同样是"只过 Python 模型"发现不了的。

### 11.4 原阻断已解除：BRAM 装不下背景帧（32K+9K 片上混合）

第一版 M5 综合通过，但**布线被 TD 拒绝**：

```
PHY-9013 ERROR: Design's emb number = 128, exceeds the limit 64.
```

根因**不在 M5**，而在 M2 的帧缓存决策（详见 §9.5）：
`bg_store.v` 的背景帧 90,240 B = 705 kbit，而 TD 只按 9K 池（64 块 = 576 kbit = 72 KB）判容量。
`behavior_fsm` 本身只占约 493 LUT / 157 FF——**M5 几乎不花钱，墙全在 M2。**

**2026-09-14 已解除**：选定"32K + 9K 片上混合"，`bg_store.v` 重写完成 →
`#bram9k 32/64` + `#bram32k 16/16`，PHY-9013 消失，M5 已出 bit。
落地细节（块号并片选、字节使能写、1 拍延迟不变）见 **§9.5 三次修正**。

三条候选路线与最终取舍：

### 11.5 TD 真实编译揪出的时序问题（一）：一行显示用的除法打穿了 sys_clk 域

M5 综合后时序报告（`syn_1/gate.timing`）：

```
clk0  cam_pclk  13.514 MHz  SWNS +56.332ns   <- 没问题
clk1  sys_clk   50.000 MHz  SWNS -30.680ns   24 个端点违规
```

10 条最差路径**全部落在 `auto_exp.v`**（M4 的模块，不是 M5）：

| # | 路径 | 逻辑级数 | 延迟 | slack |
|---|---|---|---|---|
| 1 | `snap_sum[22]` → `u_aexp/exp_mean_reg[0].d` | **48**（ADDER=32 + LUT2=16） | **50.564 ns** | **−30.680 ns** |
| 2..8 | 同源，`exp_mean_reg[1..7]` | 45→27 | 47.9→29.2 ns | −28.0 → −9.3 ns |
| 9,10 | `snap_sum[12]` → `u_aexp/pend_data_reg[14]/[12].d` | 16 | 21.3 ns | −1.4 ns |

**根因**是 `auto_exp.v` 里这一行：

```verilog
// 均值显示用：sum / 90240（除数是常量，TD 会综合成"乘倒数 + 移位"）   <- 注释是错的
wire[31:0] mean_c = frm_sum / `CAM_FRAME_PIX;
```

TD **不会**把"除以常量"自动做 strength reduction 变成"乘倒数 + 移位"，
它老老实实搭了一个 **32 级组合恢复余数除法器**——逻辑级数 48、延迟 50.6 ns，
而 sys_clk 的周期只有 20 ns。**8 个违规端点全来自这一行**，而它算出来的
`exp_mean` 只是状态行里的 `Y=`（纯显示字段，不参与控制律）。

**修法**：改成"乘倒数 + 右移"，并把安全性证明写进注释与模型：

```
mean = (frm_sum × 186) >> 24     // 186 / 2^24 = 1.108665e-5 ≈ 1/90240，偏差 +0.046%
```

- `frm_sum` 有硬上界 `90240 × 255 = 23,011,200`（25 位）→ 乘 186 后最大
  **4,280,083,200 < 2^32**，32 位中间积**不可能溢出**；
- 右移 24 位后最大 `255.13 → 255`，正好落在 8 位字段内；
- `186 = 128+32+16+8+2`，全用移位相加，逻辑级数从 48 降到个位数级；
- 0.046% 的偏差对显示用的 `Y` 无影响（模型里用**全域界**而不是抽样来断言
  "偏差 < 1 LSB"，见 `sim_vision_sub_m4.py` 的 `test_mean_reciprocal`）。

> 第 9/10 条（`pend_data`）就是下面 §11.5.1 的主角——它最终确实必须靠**插流水**解决。

> **修复后实测**（同一工程重跑 syn）：
>
> ```
>                         修复前        修复后
> sys_clk SWNS          -30.680ns     -1.379ns
> sys_clk 最大逻辑级数        48           16
> 违规端点                   24           16
> LUT                     6039         5554
> DSP                        2            4
> ```
>
> 8 条除法路径全部消除。**剩下 16 个端点全部收敛到同一条热点**：
> `snap_sum → u_aexp/pend_data_reg[*]`（逻辑级数 16、延迟 ≈21 ns）。

> **教训（比这个 bug 本身更重要）**：`/` 和 `%` 在 RTL 里**对常量也一样危险**——
> 别指望综合器替你做数学化简。这类问题只能用真实编译的时序报告发现，
> 而且它在 M4 就存在了，只是因为 M4 从未被真正编译而一直潜伏。

#### 11.5.1 收尾：`pend_data` 路径用两级流水线解决

`snap_sum → pend_data` 是整条曝光决策链：

```
fsum → 比较/减法 → |err| → 乘 → 移位 → 钳位 → 边界钳位 → pend_data
```

它一直到最后都没自己收敛，过程按顺序记下来（每一步都有真实报告）：

**第一步：先把 `frm_sum` 截到 25 位（无损，但不够）**
`frm_sum` 的硬上界是 `90240×255 = 23,011,200 < 2^25`，高 7 位恒 0；而原来直接拿 32 位的
`frm_sum` 去比较/相减，TD 就老老实实搭 32 位进位链。截到 25 位后 gate 级 slack
`-1347ps → -949ps`、LUT 5722 → 5675。
（注意 `errmag` 原本就只取 `diff[24:0]`，即"25 位"这个前提在设计里早就成立，这一步只是
把它提到前面让 TD 也能利用。）

**第二步：真实 P&R 的结果——gate 估计会骗人，而且逐次会漂**

| 跑次 | gate 级 slack | P&R 后 slack | 违例端点 | 最差路径 |
|---|---|---|---|---|
| 原始 | −1347ps | **−296ps** | 6 | AEC 链 |
| 截 25 位后 | −949ps | **−520ps** | 13 | 还是 AEC 链 |

同一个方向的优化，P&R 反而变差——**说明"最差路径是谁"在逐次布局之间会漂**，
判断依据必须是"整个域闭没闭合"，而不是某一次的 WNS 数字。结论：链条本身太长，
必须在中间切断。

**第三步：切成三段流水（真正的解）**

```
段1  fsum  -> diff -> errmag_r                 （比较 + 减法）
段2  errmag_r -> psh -> raw -> step_c_r         （乘 + 移位 + 钳位）
段3  step_c_r -> dec_amt/inc_amt -> pend_data   （边界钳位 + 回写）
```

**为什么插流水完全不需要改功能语义**：`frm_sum` 与 `exp_shut` 在一帧内都是**准静态**的
——前者整帧不变，后者只在回写那一刻变；而事件间隔是整整一帧（16.7 ms），
远大于 2 个 `sys_clk`（40 ns）。多等两拍只是让决策晚 40 ns 生效，对闭环收敛毫无影响。

**配套改动（漏了就是功能 bug）**：每加一级流水，消费端的取样脉冲就要多推一拍。
`top_vision_m5.v` / `top_vision_m4.v` 里的 `frame_tick` 从 `mt_dly[3]` 挪到 **`mt_dly[5]`**
（`mt_dly` 相应从 4 位加宽到 6 位），保证行为状态机在流水线**出结果之后**才取样。
两个顶层都要改——`auto_exp.v` 是 M4/M5 共享的。
M4/M5 的 Python 模型按"帧"建模（一次 `frame()` = 一帧），不建这条链的拍级细节，
所以模型与既有断言不受影响（这一条是改动前特意核对过的）。

**最终实测（M5 全流程，`phy_1`）**：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| sys_clk SWNS（布线后） | **−520ps**（13 个违例端点） | **+6223ps**（**0** 个违例端点） |
| sys_clk Fmax | 48.7 MHz | **72.6 MHz** |
| cam_pclk SWNS | +49.2ns | +52.4ns |
| 违例端点（全设计） | 13 | **0** |

bit 正常产出（`vision_sub_m5.bit`）。**至此 M5 综合 0 ERROR、布线时序全闭合、出 bit 完成。**

> **模型同步**：`sim_vision_sub_m4.py` 的 `parse_mean_recip` 原本硬匹配 `frm_sum`，

9. 全程 `N=016080`，且 `F`/`M`/`P`/`S`/`E`/`G`/`Y`/`L`/`V` 与 M4 表现一致

### 11.7 已修：SCCB 两线极性不定 → FPGA 自动探测（2026-09-14，`b216cf7`）

**现场现象**（M1 基础链路串口；用户描述为"摄像头转动时数值检测反馈大量相同数值"）：

```
MH1 F V=FFFF S=000B9C L=01 H=FF N=058200
```

| 字段 | 值 | 读法 |
|---|---|---|
| 自检标志 | `F` | SCCB 自检失败 |
| `V` | `FFFF` | 读 `R0x00` 无应答（读到的是上拉电平） |
| `N` | `058200` | `0x058200` = 360,960 = **752 × 480** = MT9V034 的**上电默认几何**；而配置表写入的 `R0x0D=0x0305`（2×2 binning）应得 376×240 = 90,240 = `016080` |

**因果链**：两线接反 ⇒ SCCB 总线无应答 ⇒ **整张配置表根本没写进传感器**
⇒ 传感器停在默认 752×480、AEC 开。DVP 那 11 根线照常工作，所以串口上
`S/L/H` 仍在变、**唯独 `V` 与 `N` 恒定** —— 这就是"大量相同数值"的来源。
RTL 本身无误（当时 425 项模型全过），问题在物理层。

**为什么会有这个坑**：总钻风 V2.1 改造后 FPC 的 TXD/RXD 变为 CMOS 的 SCL/SDA，
但逐飞《总钻风摄像头使用说明 V2.7》§7.2 只说"用户自行用 IIC 协议配置"，
**未指明 TXD/RXD 谁是 SCL**；转接板 V3.1 原样透传到 J1-14/J1-15 → 50/50 两可。

**方案**：不赌线序，FPGA 上电探测。

| 文件 | 改动 |
|---|---|
| `sccb_master.v` | `scl` 端口 `output→inout`；新增 `swap` 输入；**协议逻辑一行未动**，只在物理层交换角色（`swap=1` 时 SCL 走 `sda` 端口推挽、SDA 走 `scl` 端口开漏靠上拉） |
| `mt9v034_cfg.v` | 状态机 11→16 态，**写表之前先探测**：以极性 0 单次读 `R0x00`，命中 `0x1324` 即锁定；否则换极性 1 再读；两次都败才 `cam_ok=0`（此时是断线/缺上拉/未供电，**不是接反**）。探测只发"读"事务、不写任何寄存器 |
| `vision_def.v` | 新增 `PROBE_GAP_CNT`（两次尝试间静默 100 µs） |
| `top_vision_m1..m5.v` | `cam_scl` 改 `inout`、新增 `sccb_swap` 线网、自检标志改三态 `K`/`W`/`F` |
| `pin.adc` | SCCB 两脚都改 `PULLUP`（两脚都可能当开漏数据线用） |
| `sim_vision_sub_m1.py` | 68→93 项：事务级探测模型（正常 1 次命中；接反恰好 2 次且两个都是读、表只跑一次且 `swap=1`；死总线两次皆 `FFFF` 且零寄存器写）＋ `swap` mux 五条线正则护栏 ＋ 五顶层一致性护栏 ＋ 三态行字节断言 |

**关键点**：探测成功后**不再重探**（配置表校验失败只重试表，避免在正确极性上反复试探）。
五顶层一致性护栏会在任一顶层漏掉 `.swap(sccb_swap)` 或 `inout cam_scl` 时直接变红
（已用"反向注入故障"验证过该护栏真的会失败）。

**构建**：TD 无头 M1/M5 双份全流程 0 ERROR、布线全设计 0 违例（M1 SWNS +9748 ps、
M5 SWNS +7221 ps，Hold 均 +30 ps）。

**上板验收**：烧 `vision_sub_m1.bit` → 期望 `MH1 K`（或 `MH1 W`）`V=1324 N=016080`；
转动/遮挡摄像头时 `V/S/N/L/H` 应**全部**变化。若仍为 `MH1 F V=FFFF`，
按序查：① SCL/SDA 是否断路；② 两线是否都被上拉；③ 摄像头 3V3 是否独立供电到位。


### 11.8 上板实测反馈与两个可用性改进（2026-09-14，`<本轮提交>`）

#### 实测现象（烧入 §11.7 的 bit 后，15 行串口样本）

```
MH1 F V=0000 S=01159F3A N=058200 L=09 H=FF
MH1 F V=0000 S=0135D886 N=058200 L=07 H=FF
MH1 F V=0000 S=0190AF25 N=058200 L=0A H=FF
...（S 每行都不同，L/H 也在变）
```

#### 判读（已对照 RTL 逐条核对，不是推测）

| 字段 | 值 | 含义 |
|---|---|---|
| 自检标志 | `F` | 两种极性都没读到 `0x1324` |
| `V` | `0000` | **最后一次**读 R0x00 的**真实总线值**（`ack` 在 `S_END` 无条件拉高，`ver_rd` 每次事务都被覆盖）→ 换极性后那次读到全 0 |
| `N` | `058200` | `0x058200` = 360,960 = **752×480** = 上电默认几何 ⇒ 配置表仍未写进传感器 |
| `S`/`L`/`H` | 都在变 | **DVP 11 根线完好、传感器活着在出图** ⇒ 供电/摄像头/数据线都没问题 |

**关键新信息**：上一版只有 `FFFF`，这一版换极性后又读到 `0000`。
⇒ **两根线的静态电平不对称：一根悬空读全 1，另一根读全 0。**
一根线在"主机已完全释放它"的读窗口里恒为 0，说明**它被外部拉住了低电平**
（有效下拉 / 短路 / 对面器件正驱动低），而不是正常的"空闲被上拉顶到高"。

**结论：接反已被排除。** 剩下三类原因（按可能性排序）：
1. **数据线缺上拉 / 上拉太弱** —— SCCB 是开漏总线，现全靠 FPGA 内部弱上拉，
   在 15–30 cm 杜邦线 + 转接板的容性负载下可能从 0 拉不回 1；
2. **某根线断路或短到地**（与 `V=0000` 直接对应）；
3. **改造未到位** —— R12/R13 未焊、或板载 51 未拆净，CMOS 的 IIC 根本没引到 FFC。

#### 建议的硬件排查顺序

1. **量静态电压**（最快定性）：给摄像头上电、FPGA 保持复位，量 **P1-5 / P1-7 对 GND**。
   正常空闲两根都该 ≈3.3 V；**哪根是 0 V，哪根就是元凶**。
2. **量通断**：P1-5 / P1-7 ↔ CMOS 改造后引出的 IIC 两脚，应接近 0 Ω 直通；
   顺手确认 R12/R13 确实焊上。
3. **补上拉**：转接板侧给两根线各加一颗 **4.7 kΩ 到 3V3**（开漏总线的标准配置）。
4. 仍不行则**降速**：把 `SCCB_DIV_NUM` 调大（100 kHz → 25~50 kHz），给弱上拉留上升时间。

#### 本轮改进（两个可用性缺口）

**① 极性探测失败自动重试**（`mt9v034_cfg.v` + `vision_def.v`）

新增 `PROBE_RETRY_CNT = 32'd100000000`（2 s @50 MHz）。`cam_ok = 0` 时，
`C_DONE` 每 2 s 自动回到 `C_PWRWAIT` 重走一遍**完整探测**（含极性重探）。
- 动机：现场排障时"改接线 → 复位重试"是最慢的一环；有了它就是"改完等 2 秒"，
  **不必每次重新烧 bit**。
- 探测成功后不再重试；一次失败的重试只发两条读事务（约 1.2 ms / 2 s），不影响采图。
- 两个"探测失败 → C_DONE"出口（`C_PR_CHK` 极性失败、`C_CHECK` 校验用尽）
  都必须**重新装载重试延时**，否则计数从陈旧值起算会立刻触发。

**② 状态行新增 `P0` 诊断字段**（`top_vision_m1.v`）

M1 状态行 **44 → 52 字节**，行尾新增 `P0=xxxx` = **第一次（极性 0）探测**读到的 R0x00
（由 `mt9v034_cfg.ver_rd0` 输出）。与 `V`（最后一次）摆在一起即可一眼分辨是哪根线不通：

```
MH1 K V=1324 S=01234567 N=016080 L=00 H=FF P0=1324     ← 正常 / 接反（W）
MH1 F V=0000 S=00000000 N=058200 L=00 H=00 P0=FFFF     ← 本机实测：一根悬空、一根被拉低
```
